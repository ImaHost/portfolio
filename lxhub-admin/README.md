# LXHUB 상담 통역 솔루션 — 운영·유지보수 및 관리자 기능 개발

| 항목 | 내용 |
|---|---|
| 기간 | 2026.09 – 2026.10 |
| 제품 | 공공기관(학교·외국인지원센터·주민센터 등)용 **실시간 상담 통역 서비스**. 상담사 단말과 민원인 단말을 짝지어 통역하는 2-단말 방식과, 기기 하나로 대면 통역하는 1-디바이스 방식 두 갈래. 28개 언어 지원 |

| 역할 | 운영·유지보수 인수(인수자), 관리자 사이트 LLM 사용량 기능 개발(백엔드·프론트엔드), LLM 연동 버그 수정 |

## 1. 운영·유지보수 인수

운영 중인 제품을 중간에 인수했습니다. 코드가 저장소 6개에 나뉘어 있고 설계 문서가 원천(SSOT)인 체계라, 먼저 아래 순서로 익혔습니다.

1. 인수인계 가이드 → 헌법 문서(불변 원칙·비목표) → 저장소별 규칙 문서
2. 이슈 트래커(월별 LX-번호)로 최근 장애·대기 작업 파악
3. 로컬 환경 구성(백엔드 venv, SSH 키, 개발 DB 터널)

작업 루프는 **카드 1건 단위**로 고정되어 있었습니다: 영향 분석 → 설계 문서(계약) 수정 → 코드 추종 → 개발 서버 반영 → 확인 → 결정이 있으면 ADR → 운영 승급(Jenkins 승인 게이트). 계약(OpenAPI·DB 사전)과 코드의 차이를 스크립트로 0으로 맞춘 뒤에만 넘어갑니다.

## 2. LLM 사용량 "Azure 실측" 기능 (LX-095)

**문제**: 관리자 화면의 LLM 사용량은 앱이 기록한 로그 기준이라, Azure가 실제로 센 토큰과 맞는지 확인할 방법이 없었습니다. 기존 실측 화면은 리소스 하나를 고정해 조회해서, 트래픽이 실제로 가는 리소스(한국 리전)를 보지 못했습니다.

**구현**

| 영역 | 내용 |
|---|---|
| 백엔드 | 연계 모델 프로파일의 엔드포인트로 **Azure 리소스를 자동 탐색**하고, (리소스 · 모델 배포) 단위로 앱 로그와 **대사**. Azure Monitor 메트릭 조회 한도 때문에 기간을 **31일 단위로 분할 조회해 합산**. 10분 캐시 |
| 프론트엔드 | 리소스 상태 줄(리전·권한) · 모델 카드(리소스 칩·토큰·비용) · Azure 429 카드 · 기간 총비용 · **모델별 비교 표**(앱 로그 ↔ Azure 실측 · 차이율) · 미등록 배포 목록 · 메타 줄 |
| 표 UX | 10행 초과 시 내부 스크롤, 머리글·합계 두 줄(비교 합계 / 앱 로그 전체) 하단 고정, 정렬 가능 머리글 상시 표시, **3단계 정렬**(값 있는 행 → 비교 불가 → 측정 불가 사유별 묶음) + 동률 보조 정렬 |
| 예외 표시 | 권한 없는 리소스는 "권한 없음" 배너, 리소스 미발견은 ARM 목록이 읽기 가능한 리소스만 돌려주는 특성을 툴팁으로 안내 |

**설계 기록**: 리소스 탐색·대사 키·31일 분할은 ADR-0019로, 화면 규칙은 화면 설계서(ADM-019)에 오너 피드백을 받으며 4회 개정. 모두 코드와 같은 커밋 흐름에 남겼습니다.

## 3. Gemini 사고 토큰 누락 수정 (LX-096)

- **증상**: Gemini 모델의 출력 토큰(`completion_tokens`)이 실제보다 적게 집계됨. 합계(`total_tokens`)는 정상.
- **원인**: Gemini 응답의 `usageMetadata.thoughtsTokenCount`(사고 토큰)를 출력 토큰에 더하지 않았음.
- **영향 확인**: 운영 로그에서 27건, 8,758토큰 누락을 집계.
- **조치**: 사고 토큰을 출력 토큰에 포함하도록 수정하고, 과거 행 보정 계획을 트래커에 기록.

## 4. 배운 것

- 운영 중인 제품은 **문서 체계와 작업 루프를 먼저 익히는 것**이 코드보다 우선이었습니다. 계약(설계 문서)이 원천이라 코드만 고치면 검사에 걸리는 구조가, 인수자 입장에서는 오히려 안전망이 됐습니다.
- 외부 API(Azure Monitor)는 **권한 범위·조회 한도·리전 전파 지연** 같은 비기능 제약이 화면 설계까지 올라옵니다. "권한 없음"과 "리소스 없음"을 구분해 보여 주는 것이 운영자의 오해를 줄였습니다.
